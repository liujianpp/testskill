# 第一部分：功能测试用例设计方法

功能测试关注的是用户视角的操作交互，而非 API 参数组合。

---

## 1. 场景法（Scenario-based Testing）— 功能测试首选

从用户故事出发，设计完整的操作路径，是功能测试最核心的方法。

**三类场景（必须全部覆盖）：**

| 场景类型             | 说明                                         | 优先级 |
| -------------------- | -------------------------------------------- | ------ |
| **主成功场景** | 最典型正向操作，输入合法数据，功能按预期完成 | P0     |
| **备选场景**   | 正向但非典型路径（空关键字、选填字段为空等） | P1     |
| **异常场景**   | 网络错误、无数据、系统异常、超时             | P1     |

**用户故事分解模板：**

```
Given（前提）：用户已登录，进入XX页面，数据库中存在/不存在XX数据
When（操作）：用户点击/输入/选择/提交
Then（结果）：页面显示/跳转到/弹出/提示
```

**示例（地址搜索）：**

```
场景一：有匹配结果
  Given: 已登录，进入地址列表页，数据库含"上海"地址
  When:  搜索框输入"上海"，点击搜索
  Then:  列表显示含"上海"的地址，总数 ≥1

场景二：无匹配结果
  Given: 搜索数据库中不存在的关键字
  When:  搜索框输入"火星社区"，点击搜索
  Then:  列表区域显示空状态提示（"暂无数据"或默认样式）

场景三：搜索框为空
  Given: 地址列表页
  When:  清空搜索框，点击搜索（或直接回车）
  Then:  显示所有地址数据（全量展示），不报错
```

---

## 2. 等价类划分（Equivalence Partitioning）

适用于功能中有输入字段的场景（搜索关键字、表单字段等）。

**输入字段等价类识别：**

| 字段       | 有效等价类               | 无效等价类                                   |
| ---------- | ------------------------ | -------------------------------------------- |
| 搜索关键字 | 已存在的地名、英文、数字 | 空字符串、纯空格、超长字符串(>255)、特殊字符 |
| 下拉选择   | 列表中的有效枚举值       | 空、不在枚举中的值                           |
| 日期输入   | 有效日期格式             | 无效格式、过去日期、未来日期（按业务规则）   |
| 数字输入   | 在范围内的整数           | 负数、小数、超出范围、字母                   |

---

## 3. 边界值分析（Boundary Value Analysis）

重点关注：

- **字符串长度**：空(0)、1个字、最大允许长度、超最大长度
- **列表条目**：0条（空状态）、1条、满页数（分页边界）、超过分页
- **数值范围**：最小值、最大值、min-1、max+1

**功能测试边界场景：**

```
空数据 → 验证空状态 UI 是否正确显示（不崩溃、有提示）
满页 → 分页控件是否正确显示（有下一页按钮）
单条 → 分页控件是否隐藏（只有1条时不显示页码）
```

---

## 4. 判定表法（Decision Table）

适用于含多条件组合业务规则的功能。

**示例（地址操作权限）：**

| 条件                         | C1 | C2 | C3 | C4 |
| ---------------------------- | -- | -- | -- | -- |
| 已登录                       | Y  | Y  | N  | N  |
| 有编辑权限                   | Y  | N  | Y  | N  |
| **动作：显示编辑按钮** | ✅ | ❌ | ❌ | ❌ |
| **动作：显示查看按钮** | ✅ | ✅ | ❌ | ❌ |
| **动作：跳转登录页**   | ❌ | ❌ | ✅ | ✅ |

---

## 5. 结对思维 / Pairwise（多输入条件优化）

当功能有多个独立输入条件时，使用 Pairwise 减少组合爆炸。

**示例（地址搜索有多重过滤条件）：**

```
A: 关键字   → [有值, 空]
B: 省份过滤 → [选择了, 未选]
C: 排序方式 → [升序, 降序]

Pairwise 组合（覆盖所有两两对）：
TC1: 有值 + 选了省份 + 升序
TC2: 有值 + 未选省份 + 降序
TC3: 空   + 选了省份 + 降序
TC4: 空   + 未选省份 + 升序
```

## 6. 错误猜测（Error Guessing）

基于常见 Bug 经验，主动设计容易出问题的场景：

| 场景                                     | 常见 Bug                         |
| ---------------------------------------- | -------------------------------- |
| 搜索特殊字符 `%`、`_`（MySQL通配符） | 查出所有数据或报SQL错误          |
| 搜索中文与英文组合                       | 编码问题导致乱码或查不到         |
| 快速多次点击搜索                         | 接口重复请求，列表闪烁或重复数据 |
| 搜索结果为0后清空关键字                  | 状态不恢复，仍显示"无数据"       |
| 页面刷新后搜索条件                       | 关键字是否保留（浏览器刷新）     |
| 超长输入超过显示区域                     | 文字溢出、样式错位               |
| 空格关键字                               | 等同空查询还是literal搜索空格    |

## 7. 功能测试步骤编写规范

步骤必须遵循：**具体页面 + 具体控件 + 具体操作 + 期望中间状态**

**示例（好的步骤）：**

```
1. 使用管理员账号（admin/Admin@123）登录系统
2. 顶部导航点击「地址管理」菜单
3. 左侧二级菜单点击「地址列表」进入地址列表页
4. 页面顶部搜索框（placeholder为"请输入地址关键字"）中输入"上海"
5. 点击搜索框右侧蓝色「搜索」按钮（或按 Enter 键）
6. 等待页面列表区域加载完成（约2秒内）
7. 核查列表数据行与搜索结果数量
8. 执行验证SQL，比对数据库结果与页面显示数量
```

**预期结果模板：**

```
UI层：
  - 页面无报错（无红色弹框、无控制台异常）
  - 列表区域显示匹配结果，每行包含：[字段1]、[字段2]、...
  - 顶部显示结果总数：共 X 条记录
  - 搜索框保留输入关键字

数据层（验证SQL）：
  SELECT COUNT(*) FROM lsp_dev.lsp_address_suburb
  WHERE suburb_name LIKE '%上海%';
  期望：COUNT 值 = 页面显示的总数
```

## 8. 测试维度覆盖检查清单

每个功能点用例设计完后，检查以下维度是否覆盖：

- [ ] 正常主流程（Happy Path）
- [ ] 空数据/无结果状态
- [ ] 输入边界（最长、最短、特殊字符）
- [ ] 权限/角色（不同用户看到的内容差异）
- [ ] 数据准确性（验证SQL与页面数据一致）
- [ ] 页面交互反馈（加载态、成功提示、错误提示）
- [ ] 浏览器刷新/回退后状态

---

## 覆盖率检查公式

```python
def check_coverage(cases):
    total = len(cases)
    dist = {t: sum(1 for c in cases if c['case_type'] == t) for t in ['正向','负向','边界','安全']}
    print(f"总用例: {total}")
    for t, n in dist.items():
        status = "✅" if n/total >= {'正向':0.4,'负向':0.3,'边界':0.2,'安全':0.1}[t] else "⚠️"
        print(f"{status} {t}: {n}/{total} = {n/total*100:.0f}%")
```

**目标：每个 API 上限 20 条用例，覆盖率满足：正向≥40%, 负向≥30%, 边界≥20%, 安全≥10%**

---

## 用例数量控制

| 功能复杂度                 | 建议用例数    |
| -------------------------- | ------------- |
| 简单查询（只读，单输入）   | 3～5 个       |
| 带过滤的列表               | 5～8 个       |
| 带增删改的 CRUD 功能       | 8～10 个      |
| 复杂业务规则（多条件判定） | 10 个（上限） |

**覆盖率目标：**

- 正向（含正常流程+数据展示）≥ 40%
- 负向（含异常流程+空数据+错误提示） ≥ 30%
- 边界（含边界值+空状态） ≥ 20%
- 安全/权限 ≥ 10%

# 第二部分：API测试用例设计方法

API测试关注接口参数组合、返回值验证和安全防护。

---

## 1. 等价类划分（Equivalence Partitioning）— API版本

将输入域划分为若干等价类（合法 + 非法），每类取一个代表值。

**对每个输入参数，识别：**

- **有效等价类**（≥2个）：能被系统正常处理的值域
- **无效等价类**（≥3个）：系统应拒绝/报错的值域

**示例（limit 字段，整型，范围 1~100）：**

| 等价类         | 代表值      | 类型         |
| -------------- | ----------- | ------------ |
| 正常范围 1~100 | 20, 50      | 有效         |
| 超出上限 >100  | 1000        | 无效         |
| 等于下限 1     | 1           | 有效（边界） |
| 等于上限 100   | 100         | 有效（边界） |
| 小于下限 <1    | 0, -1       | 无效         |
| 非整数类型     | "abc", null | 无效         |

---

## 2. 边界值分析（Boundary Value Analysis）— API版本

在等价类边界处取值，覆盖：`min`, `min+1`, `max-1`, `max`, `null/empty`

**字符串字段边界：**

- empty string `""`
- 单字符 `"a"`
- 最大长度（如255） → `"a"*255`
- 超最大长度 → `"a"*256`
- 含特殊字符 `"特殊!@#"`

**数值字段边界：**

- `0`, `1`, `max_int`, `-1`, `max+1`

**分页参数专项：**

- page=0（边界）、page=-1（无效）、page=99999（超大）
- limit=0（无效）、limit=1（最小）、limit=最大限制值

---

## 3. 结对思维 / Pairwise Testing（API版本）

用于参数组合爆炸场景，确保每**两个参数**的所有取值组合至少被一个用例覆盖。

**步骤：**

1. 列出所有参数及其取值集合
2. 构建参数因子表
3. 使用正交表方法选取最少测试组合覆盖所有参数对

**示例（地址搜索 POST /address/search）：**

```
因子矩阵：
A: keyword   → [null, 有效, 注入]
B: limit     → [正常(20), 最小(1), 无效(0)]
C: page      → [正常(1), 第2页, 无效(-1)]
D: orders    → [null, ASC, DESC]
E: queries   → [null, 有效字段]

结对覆盖目标：
(A,B), (A,C), (A,D), (A,E)
(B,C), (B,D), (B,E)
(C,D), (C,E)
(D,E)
```

**贴标签方法**：每条用例备注中记录覆盖的参数对，如：
`notes: "Pairwise: A=有效,B=20,C=1,D=ASC,E=null"`

---

## 4. 场景法（Scenario-based Testing）— API版本

描述端到端业务场景，包含完整上下文。

**场景分类：**

- **主成功场景**：典型正向业务流程
- **备选场景**：正常但不典型的路径
- **异常场景**：预期内的错误处理
- **异常中断场景**：网络中断、超时等

**模板：**

```
前提：[初始状态]
when/时间：[触发条件]
步骤：[有序操作序列]
then/结果：[期望结果]
```

---

## 5. 错误猜测（Error Guessing）— API版本

基于经验主动猜测系统可能出现的错误。

**常见缺陷猜测点：**

| 场景       | 猜测的问题                              |
| ---------- | --------------------------------------- |
| 字符串字段 | 未过滤 SQL 特殊字符（',";--）           |
| 数值字段   | 未校验负数、零、超大值                  |
| 分页参数   | page*size 溢出整型                      |
| JSON Body  | 缺少必填字段时返回 500 而非 400         |
| 空列表返回 | 返回 null 而非空数组 []                 |
| 联合查询   | keyword 与 queries 同时传入产生逻辑冲突 |
| 排序字段   | 传入不存在的字段名、SQL 保留字          |
| 中文关键字 | 编码问题导致乱码或查不到                |

---

## 6. 数据库约束驱动的用例生成

从表结构中提取约束，自动生成对应负向用例。

| DB 约束       | 对应测试思路                         |
| ------------- | ------------------------------------ |
| NOT NULL      | 传 null/空 → 期望报错               |
| UNIQUE        | 插入重复值 → 期望唯一键冲突错误     |
| VARCHAR(n)    | 传超长字符串 → 期望截断或报错       |
| TINYINT(1)    | 传 2/3/-1 → 期望报错                |
| ENUM('A','B') | 传 'C' → 期望报错                   |
| FK 外键       | 传不存在的外键值 → 期望报错         |
| DEFAULT       | 不传该字段 → 验证 DB 中使用了默认值 |

---

## 7. 安全测试用例设计

**针对每个字符串类型输入参数：**

| 类型     | 测试 payload                  | 期望行为                    |
| -------- | ----------------------------- | --------------------------- |
| SQL 注入 | `' OR '1'='1' --`           | 200空/400错误，不暴露DB信息 |
| SQL 注入 | `'; DROP TABLE users; --`   | 同上                        |
| XSS      | `<script>alert(1)</script>` | 字段内容被转义或拒绝        |
| 路径穿越 | `../../../etc/passwd`       | 400 或内容被过滤            |
| 超大载荷 | 10000 字符的字符串            | 400 或截断，不崩溃          |
| 空白字符 | `"   "` (仅空格)            | 合理处理（视为空或报错）    |
| Unicode  | ` `（null字节）        | 400 或过滤                  |
