# prd-review 使用说明

**测试视角需求评审**技能（Claude Code / Cursor 通用）：对需求文档（PRD 等）**仅从测试视角**按 **5 个维度**评审，输出结构化 Markdown 评审报告。不做完整产品/研发向 PRD 评审，也不生成全量测试用例。

---

## 1. 输入与输出

| 项目 | 说明 |
|------|------|
| 输入 | `.pdf` / `.docx` / `.md` / `.txt` 文件路径，或直接粘贴的需求正文 |
| 正文抽取 | pdf/docx 走 `python scripts/extract_text.py <路径>`（依赖 `pdfplumber`、`python-docx`，缺失提示 `pip install pdfplumber python-docx`）；md/txt 直接读 |
| 输出 | Markdown 评审报告，默认当前工作目录 `test-review-report.md`（可指定路径） |
| 抽取失败 | 扫描件无文字层/加密/损坏 → 明确报错，**禁止编造**文档内容 |

## 2. 工作流程（7 步）

```
1 抽取正文 → 2 确认元信息(标题/版本/作者，不足则注明假设) → 3 提炼需求速览 → 4 按 5 维全量评审 → 5 总体结论 → 6 按模板落盘 → 7 只回复报告路径
```

**需求速览**（写在元信息表与分维度评审之间）：

| 小节 | 要求 |
|------|------|
| 需求在讲什么 | 1–3 句：业务目标、范围内/外 |
| 端与角色 | 表格：端/角色、使用者、能力边界 |
| 功能模块 | 表格：模块、端、测试关注点一句话 |
| 核心业务主流程 | 默认 1 张 Mermaid flowchart；有清晰状态枚举可再附 1 张状态图，**最多 2 图**（节点 ID 用 camelCase，标签含特殊字符加双引号） |

仅提炼已写内容，禁止臆造；不扩写产品方案、不写全量用例。

## 3. 五个评审维度（全部评审，不可只评部分）

| # | 维度 | 核心检查点 |
|---|------|-----------|
| 1 | **可测性与验收标准** | 核心需求可写成可判定验收条件（Given/When/Then 或等价）；成功/失败有可观察结果；避免「体验良好」「适当处理」等不可判定表述；关键阈值有数字 |
| 2 | **边界与异常** | 空值/超长/非法/特殊字符；权限不足/未登录；失败超时重试；并发/重复提交/幂等；上限配额分页；破坏性操作的确认与失败表现 |
| 3 | **场景与状态** | 主流程步骤完整；关键分支（取消/中断/返回/二次进入）；状态定义与迁移；角色差异；多端/多入口差异 |
| 4 | **数据与环境依赖** | 测试数据前提（账号/配置/开关）；外部依赖标明；环境差异与造数/mock 可行性；时间相关可模拟；清理/回滚要求 |
| 5 | **测试阻塞点** | 开放问题是否卡住设计/执行；规则矛盾术语冲突；缺权限/账号/工具；不可测点显式标出；回归影响面提示 |

每个维度先给结论（通过 / 有条件通过 / 不通过），再列问题表；无问题写「未发现问题」。

## 4. 问题级别与总体结论

**每条问题必含 4 字段**：级别、原文依据（章节名或摘录）、问题、建议。

| 级别 | 含义 |
|------|------|
| `阻断` | 无法设计/执行关键测试，前必须补齐 |
| `重要` | 测试设计前应处理 |
| `建议` | 可排期完善 |

| 总体结论 | 条件 |
|----------|------|
| 不通过 | 存在任意 `阻断` 问题 |
| 有条件通过 | 无阻断，但有 `重要` 问题 |
| 通过 | 仅 `建议` 或无明显问题 |

问题以分维度 Markdown 表格呈现（维度由小节标题体现，不另做汇总清单）：

```markdown
| 级别 | 原文依据 | 问题 | 建议 |
|------|----------|------|------|
| 阻断 | 「完成注册流程」 | 无可判定验收条件 | 补充：验证码校验成功且进入首页 |
```

## 5. 使用方式

把需求文档给到后直接说：

```text
评审这份需求文档 docs/xxx-PRD.pdf
（或粘贴正文 + 「按测试视角评审」）
```

完成后技能只提示报告路径（`test-review-report.md`），不在对话复述全文。报告结构见 `references/report-template.md`，维度清单见 `references/dimensions.md`。

## 6. 在工作区中的角色

prd-review 是 **testflow 全流程的第一环**（需求评审 → spectest 用例设计 → 三支线执行 → 统一报告），也可单独使用。
