# 测试视角需求评审

根据用户提供的需求文档（或粘贴正文），**仅从测试视角**按 5 个维度评审，并输出 Markdown 报告。  
不展开完整产品/研发 PRD 评审，也不在本 skill 中生成全量测试用例。

## 输入与输出

| 项目 | 说明 |
|------|------|
| 输入 | `.pdf` / `.docx` / `.md` / `.txt` 文件路径，或直接粘贴的需求正文 |
| 输出 | Markdown 评审报告 |
| 路径 | 用户指定则用指定路径；否则写入当前工作目录 `test-review-report.md` |

评审维度见 [references/dimensions.md](references/dimensions.md)（评审前必读）。  
报告结构见 [references/report-template.md](references/report-template.md)。

## 工作流程

### 1. 抽取正文

| 格式 | 处理方式 |
|------|----------|
| `.md` / `.txt` | 直接 `Read` |
| `.pdf` / `.docx` | 运行本 skill 下脚本：`python scripts/extract_text.py <绝对或相对路径>` |
| 粘贴正文 | 直接作为需求正文 |

脚本依赖：`pdfplumber`、`python-docx`。若缺失，提示用户执行：

```bash
pip install pdfplumber python-docx
```

抽取失败（扫描件无文字层、加密、损坏等）时明确报错，**禁止编造**文档内容。

### 2. 确认文档元信息

从正文提取或合理标注：标题、版本/日期、作者（若有）。  
信息不足时用 1–2 句写明假设，无需反复追问用户。

### 3. 提炼需求速览

在五维评审之前，基于正文提炼「需求速览」（写入报告元信息表与「分维度评审」之间），便于测试理解：

| 小节 | 要求 |
|------|------|
| 需求在讲什么 | 1–3 句：业务目标、范围内/外 |
| 端与角色 | 表格：端/角色、使用者、能力边界 |
| 功能模块 | 表格：模块、端、测试关注点一句话 |
| 核心业务主流程 | 默认 1 张 Mermaid `flowchart`；若有清晰状态枚举可再附 1 张状态图，**最多 2 图** |

仅提炼文档已写内容，禁止臆造未写能力；篇幅精简，不扩写产品方案，不写全量用例。  
Mermaid：节点 ID 用 camelCase；标签含特殊字符时加双引号。

### 4. 按 5 维全量评审

必须读取 [references/dimensions.md](references/dimensions.md)，对以下维度**全部**评审，不可只评部分：

1. 可测性与验收标准
2. 边界与异常
3. 场景与状态
4. 数据与环境依赖
5. 测试阻塞点

每条问题必须包含：

- **级别**：`阻断` / `重要` / `建议`
- **原文依据**：章节名或简短摘录
- **问题**
- **建议**

（所属维度由分维度小节标题体现，勿再输出独立「问题清单」汇总节。）

### 5. 给出总体结论

| 结论 | 条件 |
|------|------|
| 不通过 | 存在任意 `阻断` 问题（文档尚不足以支撑测试设计/执行） |
| 有条件通过 | 无阻断，但存在 `重要` 问题 |
| 通过 | 仅有 `建议` 或无明显问题 |

### 6. 落盘报告

严格按 [references/report-template.md](references/report-template.md) 生成完整 Markdown（含需求速览），写入约定路径。

### 7. 回复用户

报告写完后，**只提示完成并给出报告文件路径**，不要在对话里复述全文或长篇总结。

## 问题条目格式

每条问题必须包含字段：级别、原文依据、问题、建议（维度由分维度小节标题体现，不再单独汇总「问题清单」）。

分维度评审用 Markdown 表格呈现：

```markdown
| 级别 | 原文依据 | 问题 | 建议 |
|------|----------|------|------|
| 阻断 | 「完成注册流程」 | 无可判定验收条件 | 补充：验证码校验成功且进入首页 |
```
