# testflow 使用说明

**测试全生命周期调度器**技能（Claude Code / Cursor 通用）：本身是「**地图 + 转换器 + 汇总器**」，不实现任何测试能力——各阶段读取对应技能的 SKILL.md 并**完整移交控制权**，阶段结束收回。把「需求评审 → 用例设计 → 三支线执行 → 统一报告 → 归档」串成一条链。

---

## 1. 全景流程（5 阶段 + 1 预热）

```
阶段1          阶段2            阶段3                阶段4        阶段5
需求评审   →   用例设计      →  执行（三支线）     →  统一报告  →  归档
prd-review     spectest 9步      3A 接口(可选)        汇总脚本     spectest-archive
                                 3B Web UI(默认)
                                 3C 小程序(可选)
```

| 阶段 | 入口技能 | 关键产物 | 触发条件 |
|------|---------|---------|---------|
| 0 预热（可选） | api-doc-generator | 接口文档 | 只有源码、没需求文档 |
| 1 需求评审 | prd-review | 5 维评审报告 MD | 默认起点 |
| 2 用例设计 | spectest new→analysis→plan(可选)→points→generate→review→fix | 25 列 `artifacts/<name>_testcases.xlsx` | 阶段 1 后 |
| 3A 接口支线 | ApiAutoTest2.0 四技能链 | docs/ 场景与用例 + Allure | **用户显式要求**或有源码且确认 |
| 3B UI 支线 | testflow 转换器 + browser-use-case-runner | `ui_cases.xlsx` + MD 报告 + 截图 | **默认支线** |
| 3C 小程序支线 | testflow 转换器 + miniprogram 三件套 | `mp_cases.xlsx` + Jest spec + Session 报告 | 用户显式声明含微信小程序 |
| 4 统一报告 | testflow 汇总器 | `artifacts/unified-report.md` | 任一支线完成后 |
| 5 归档 | spectest-archive（可选 operation-manual） | 归档目录 / 操作手册 | 用户确认后 |

**默认链路：1 → 2 → 3B → 4**。

## 2. 状态目录与断点续跑

状态根 = 目标项目 `spectest/changes/<name>/`（复用 spectest 约定）。恢复时按产物判断进度：

| 已有产物 | 说明阶段 |
|----------|----------|
| `artifacts/*_testcases.xlsx` | 阶段 2 已完成 |
| `artifacts/ui_cases.xlsx` | 3B 转换已完成 |
| UI MD 报告 | 3B 已执行 |
| `artifacts/api/` 说明文件（allure_path.txt） | 3A 已执行 |
| `artifacts/mp/` 说明文件（report_path.txt） | 3C 已执行 |
| `artifacts/unified-report.md` | 阶段 4 已完成 |

**每阶段结束向用户复述（产物+统计+下一步），用户确认后才推进，不自动串联。**

## 3. 各阶段要点

- **阶段 2 停靠策略**：`test-plan.md` 与 `design.md` 在本流程内「不停等」——生成后直接继续，供事后审阅（单独跑 spectest 技能时才停靠）。25 列中「API URL」非空的行是 API 用例（→3A 线索），其余 →3B。
- **3B 转换**（在 `spectest/changes/<name>/` 下执行）：
  ```bash
  python <testflow-skill-dir>/scripts/convert_25col_to_ui_xlsx.py -i artifacts/<name>_testcases.xlsx -o artifacts/ui_cases.xlsx
  ```
  导出 0 行停下询问；再交 browser-use-case-runner 执行（需确认 URL 与会话策略）。
- **3C 前置**（首次）：`scaffold.sh` + 配 `miniprogram.local.config`（**Windows 的 cliPath 须为本机微信开发者工具路径**，示例 macOS 路径不可用）+ npm 依赖 + `MP_ACCOUNT/MP_PASSWORD`。转换与 3B 同一转换器，仅输出名 `mp_cases.xlsx`（8 列与 miniprogram `parse-testcases.js` 表头兼容）。
- **阶段 4 五源汇总**（缺哪个跳哪个；`--ui-report/--mp-report` 路径不存在时静默跳过不报错）：
  ```bash
  python <testflow-skill-dir>/scripts/aggregate_reports.py \
    --excel artifacts/<name>_testcases.xlsx \
    [--allure-dir <allure-results>] [--ui-report <UI MD>] \
    [--mp-report <mp 台账或 Session 报告>] [--playwright-json <web 的 playwright-results.json>] \
    --output artifacts/unified-report.md
  ```

## 4. 格式契约

- **25 列 → runner 8 列映射**：用例编号←测试项/测试点、用例名称←用例标题、功能模块←模块、优先级←用例优先级、前置/步骤直传、测试数据←测试数据准备、预期结果直传
- **API 用例判定**：25 列「API URL」非空
- **统计口径**：通过率 = 通过/(通过+失败)，阻塞单列不进分母
- **双链路独立**：需求驱动链路（prd-review→spectest）与代码驱动链路（api-doc-generator→…）互不转换，仅在阶段 4 汇合；3B 与 3C 同源分流、互不转换

## 5. 硬性规则

- 不修改各技能内部逻辑与产物格式；不做 testcases.json ↔ cases.json 互转
- 每阶段复述等确认；验证码/人工介入遵循 case-runner 自身停等规则
- 3C 结论只认 miniprogram-run 的 Session 报告/台账（script-author 产物属「待校验」）

## 6. 使用方式

```text
「跑一次完整 testflow，需求文档在 docs/PRD.pdf，被测地址 https://xxx」
（小程序端补一句：「包含微信小程序端」；接口自动化补一句：「后端源码在 backend/，要跑接口支线」）
```
