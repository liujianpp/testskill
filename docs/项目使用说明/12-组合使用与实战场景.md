# 12 · 组合使用与实战场景（重点推荐）

> **本册回答你的两个问题**：技能怎么**组合**使用？组合起来有**什么作用**？
> 内含 7 个可照抄的完整实操场景。先看 §1 组合逻辑，再挑跟你处境像的场景照着做。

## 1. 组合的总逻辑

### 1.1 各技能可以单独用，也可以串起来用

单独用：只评审需求（prd-review）、只执行一张用例表（case-runner）、只出手册（operation-manual）……都没问题。

串起来用的**两个粘合剂**：

| 粘合剂 | 作用 |
|--------|------|
| **25 列标准 Excel** | 全工作区「通用货币」：spectest 生成它 → 转换器转成各执行器格式 → 分拣脚本按它入库 |
| **testflow 调度器** | 按流程自动切换技能、传递产物、最后汇总报告 |

### 1.2 产出与消费关系（谁喂谁）

| 套件 | 吃什么 | 吐什么、喂给谁 |
|------|--------|----------------|
| prd-review | 需求文档 | 评审报告 → 人看 / 附给 spectest |
| spectest | 需求文档 | 25 列 Excel → 三支线 / 资产库 |
| ApiAutoTest2.0 | 后端源码 | Allure 报告 → 统一报告 |
| seed-test-data | 接口文档/HAR/curl/表结构 | 造数文件（Postman/SQL/Excel/Python）→ 各支线执行前的数据准备 |
| browser-use-case-runner | 8 列 xlsx/MD/手动用例 | MD 报告+截图 → 统一报告 |
| miniprogram | mp_cases.xlsx | Session 报告+台账 → 统一报告 |
| web-script-author | 25 列 UI 用例 | Playwright 脚本 → test-automation/web → CI |
| test-automation | 各处沉淀的资产 | 每日回归结果 + 晋级台账 |

### 1.3 两条独立链路（不要混）

- **需求驱动链**：prd-review → spectest →（转换）→ 三支线执行 —— 从需求出发；
- **代码驱动链**：api-doc-generator → scenario → generator → runner —— 从源码出发；
- 两条链**互不转换用例**，只在**统一报告**（testflow 阶段 4）汇合。

## 2. 五种经典组合方式

### 组合一：全流程一条龙（testflow）

**适合**：新需求来了，从零到报告一把梭。
**作用**：一句话启动，AI 按阶段推进，你只管在每个关口确认。

```
你说一句话 → prd-review 评审 → spectest 出 25 列 → 自动转 8 列
→ browser-use-case-runner 有头执行 → 五源汇总统一报告 → 归档
```

### 组合二：全流程 + 接口支线（testflow 3A）

在组合一的话术里加一句「后端源码在 backend/，要跑接口支线」。
25 列中「API URL」非空的行被识别为接口线索 → ApiAutoTest2.0 四技能链执行 → Allure 结果并入统一报告。
**作用**：一套需求，UI 和接口双覆盖。

### 组合三：全流程 + 小程序支线（testflow 3C）

加一句「包含微信小程序端」。同一份 25 列 → 转出 `mp_cases.xlsx` → script-author 写脚本 → run 执行 → 报告并入统一报告。
**作用**：同一批功能用例在网页端和小程序端各验证一遍，结果分列对比（3B/3C 可同时开、互不干扰）。

### 组合四：测试结果沉淀为永久回归资产

```
本次迭代的 25 列用例
   ├─► promote_cases.py 分拣入库（回归用例→main，其余→iterations/版本号）
   └─► web-script-author 把 UI 用例转成 Playwright 脚本
         └─► 每晚 02:17 CI 自动回归 main 主干
迭代上线 ─► promote_iteration.py 晋级进 main
```

**作用（这套组合的终极价值）**：**一次测试投入，变成永久回归能力**——以后每晚 CI 自动验证核心链路，不再需要人肉回归；迭代资产经两轮全绿后晋级主干，回归集越滚越大。

### 组合五：只有代码、没有需求（代码驱动链）

```
api-doc-generator（扫源码出接口文档）
   ├─► api-scenario-generator → api-test-generator → api-test-runner → Allure
   └─► （可选）接口文档反过来当 spectest-analysis 的输入，补需求视角用例
```

**作用**：老系统没文档也能测；接口文档顺便成了团队资产。

## 3. 七个完整实操场景（照抄话术）

### 场景 A：产品给了 PRD → 评审 + 出用例（最常见）

**第 0 步**：cd 到**被测项目**根目录，打开 Claude Code。

```
1. 「对 docs/PRD-积分商城v2.docx 做测试视角的需求评审」
   → 得 test-review-report.md；把「阻断」问题反馈产品
2. 「/spectest-new 创建变更 jifen-v2，需求文档 docs/PRD-积分商城v2.docx」
3. 「/spectest-analysis 分析需求」
4. 「/spectest-points 推导测试点」
5. 「/spectest-generate from-specs 导出 Excel」
6. 「/spectest-review 评审用例」→「/spectest-fix 按评审意见修复」
   → 产物：spectest/changes/jifen-v2/artifacts/jifen-v2_testcases.xlsx
```

### 场景 B：只有后端源码 → 接口自动化全套

```
1. 「扫描 backend/ 生成接口文档」
2. 「基于接口文档设计订单模块的业务场景，登录放依赖里」
3. （首次）「帮我配置前置依赖和数据库断言」
4. 「把场景转成可执行用例」
5. 「执行 docs/order_cases.json，base-url https://test.example.com」
6. 「打开 Allure 报告」
   → 跑挂了看修复建议，你决定改不改
```

### 场景 C：已有一张用例表 → 网页上真机执行

```
1. 确认用例表含推荐列（编号/名称/模块/优先级/前置/步骤/数据/预期），存 test-data/登录用例.xlsx
2. 「用 browser-use-case-runner 执行 test-data/登录用例.xlsx，被测地址 https://test.example.com」
3. 回答它的简短确认 → 看着浏览器自动跑（弹验证码就在对话里回内容）
4. 拿到 reports/case-run-xxx.md + 截图，直接可汇报
```

### 场景 D：一句话全流程（AI 全托管）

> 「跑一次完整 testflow，需求文档在 docs/PRD.pdf，被测地址 https://test.example.com，后端源码在 backend/ 跑接口支线」

每个阶段结束它会停下来汇报等你确认；中断了再发一次 `/testflow` 从断点续跑。
最终产物：`artifacts/unified-report.md`（总览/需求覆盖/明细/风险四节）。

### 场景 E：把本次测试沉淀成每日回归

```
1.（本仓库）「把 spectest/changes/jifen-v2/artifacts/jifen-v2_testcases.xlsx 分拣入库，版本 2026Q4-jifen，先 dry-run」
2. 「用 web-script-author 把其中 UI 用例转成 Playwright 脚本，落位 web/iterations/2026Q4-jifen，
     被测地址 https://test.example.com」
3. 「npx playwright test web/iterations/2026Q4-jifen」本地验证两轮全绿
4. 迭代上线后：「把 2026Q4-jifen 晋级进主干，先预览再 confirm」
   → 从此每晚 02:17 CI 自动回归
```

### 场景 F：给系统写用户手册（与测试并行的小任务）

> 「给 https://oa.example.com 生成操作手册，账号 test01，覆盖请假、报销模块」

→ 得到 `{产品名}-操作手册/`（MD + 全套截图），可直接发业务方。
（testflow 阶段 5 归档时也可以顺手来一份。）

### 场景 G：执行前先造数（seed-test-data + 任意执行支线）

**适合**：用例的前置条件要一堆账号/订单/业务数据，手动点半天——先让 AI 出造数文件。

```
1. 「根据 docs/api-docs.md 造一套完整数据：公寓→房间→租客→入住，正常+异常各 1 条，
     要 Postman 和 Python」（也可喂 HAR 抓包 / curl / 建表 SQL）
2. 它给清单勾选 → 生成文件；你导入 Postman 跑「造数」文件夹
   （Python 版：.env 填 SEED_BASE_URL/SEED_TOKEN 后 python3 script/xx-api-seed.py seed）
3. 拿 QA_ 前缀的账号/单号去跑 UI 用例（05 册）或接口用例（04 册）
4. 用完清理：Postman 跑「回滚」文件夹 / python3 ... rollback（SQL 版手工执行 02_rollback.sql）
```

**要点**：它只出文件不执行；数据可追溯（QA_ 前缀）、回滚按精确业务键删不误删。详见 [17 册](17-技能详解-seed-test-data-测试造数.md)。

## 4. 组合使用的三个心得

1. **口径统一靠 25 列**：不管走哪条支线，源头都是 spectest 的 25 列 Excel——用例编号全程不变，报告能对回需求；
2. **人和 AI 的分工**：AI 负责「跑流程、出产物、给建议」；你负责「关口确认、阻塞决策（验证码/不可逆操作）、用例修复取舍」；
3. **沉淀比执行更值钱**：单次执行是「一锤子买卖」，组合四的资产沉淀让每次迭代的产出累积成回归体系——这是整套工作区最大的作用。
